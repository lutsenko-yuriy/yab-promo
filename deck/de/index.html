1 · Zweck

Agenten schreiben Code. Wer steuert den Prozess?

  • Allein überspringt ein Agent unter Zeitdruck Planung, Tests und Review
  • Jede Session beginnt bei null: kein Backlog, keine Erinnerung an frühere Entscheidungen
  • Eine Person allein kann nicht alles prüfen, was ein Agent erzeugt

1 · Zweck

YAB ist eine GitHub-Vorlage

Skills

Jeder Arbeitsschritt ist ein Skill: brief, plan, implement, review, ship

Workflow

Tickets, Work Units, TDD, ein PR pro Work Unit

Gedächtnis

Wissensbasis, Entscheidungen und Debriefs liegen im Repo

Gate

Erst konfiguriert /onboard das Projekt, dann läuft alles andere

1 · Zweck

Fünf Skill-Familien

configure

onboard, calibrate, style, skill-creator

design

brief, analyze, plan, research, experiment

build

implement

verify

review, audit, draft-scenarios

manage

summarize, ship, debrief, note, checkup

Skills verlangen eine Aufwandsstufe und eine Denktiefe, keinen Modellnamen. Die Zuordnung zu den vorhandenen Modellen erfolgt einmalig mit /calibrate.

2 · Beispiel Beispiel-Ticket folgt

Ein Ticket, mehrere Work Units

/summarize/brief/plan WU0WU1…N/debrief/ship

/summarize eröffnet die Session: Hier ist das Backlog, was kommt ins nächste Release?

2 · Beispiel

Ein Ticket, mehrere Work Units

/summarize/brief/plan WU0WU1…N/debrief/ship

/brief macht aus einer groben Idee ein klar umrissenes Ticket, Frage für Frage.

/plan zerlegt es in Work Units, jede mit eigenem Branch und PR. Der Plan wird freigegeben, bevor Code entsteht.

2 · Beispiel

Ein Ticket, mehrere Work Units

/summarize/brief/plan WU0WU1…N/debrief/ship

WU0 kommt vor jedem Produktionscode: rote Integrationsszenarien für den Nutzerfluss oder eine Prüf-Checkliste für alles andere.

2 · Beispiel

Ein Ticket, mehrere Work Units

/summarize/brief/plan WU0WU1…N/debrief/ship

Jede Work Unit durchläuft dieselbe Schleife:

roter TestgrünRefactoring + Commit PR/review + /auditKorrekturen

Zwischenstände tragen das Tag [wip], damit Tester nie ein halbes Feature bekommen.

2 · Beispiel

Ein Ticket, mehrere Work Units

/summarize/brief/plan WU0WU1…N/debrief/ship

/debrief hält eine kurze Retrospektive und speichert die Erkenntnisse in der Wissensbasis.

/ship schließt das Ticket, schreibt das Changelog, erhöht die Version und merged.

Was es noch nicht kann

  • Erprobt von einem Entwickler mit Agenten, nicht von einem Team
